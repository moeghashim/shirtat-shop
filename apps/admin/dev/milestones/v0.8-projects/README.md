## Brief and boundaries

Give a developer evaluating tenboards a coherent sample workspace: Home summarizes work across projects, Projects finds a project, and each project offers Overview, Board, List, Timeline and Files. Board/List show the same tasks. Timeline incorporates the current Calendar domain; Files incorporates File Manager. Existing standalone URLs become permanent redirects after all destinations are usable.

Use the existing v0.4 demo/DB selection, typed server functions, request-scoped Workers runtime and v0.5 authentication. All signed-in users continue to see shared sample records. Project membership is sample metadata, **not authorization, tenancy or an auth-user mapping**. Public demo and PR previews remain zero-secret demo mode. No CRUD, drag-to-mutate tasks, uploads/download service, invites, sharing changes, favorite mutations, notifications, dependency editing, RBAC, multi-tenancy or new runtime dependency. Mail, Chat, Invoice, Products, Users, Roles, Profile and the ten current dashboard examples retain their behavior. Assistant remains v0.7-owned.

This is documentation only. The user's planning assignment authorizes this new `dev/milestones/` contract despite the generic dev-file restriction, and specifies `docs/v0.8/000-milestone-plan`. PLAN, existing task contracts, runtime/configuration, dependencies and protected components remain untouched. Implementation requires planning review and a separately approved task.

### Migration, seed and reads

- Migration creates new tables/constraints/indexes and **backfills existing board/ledger rows and file/calendar links**, using deterministic IDs and explicit mappings. Unknown adopter records get conservative fields (unassigned/undated when unavailable); do not discard them. Preserve old tables and old reads as compatibility seams during rollout. Existing schema/data, auth records, unrelated dashboards and migration history survive; no destructive reset or legacy-table drop in v0.8.
- Extend transactional, idempotent seed ordering: people/projects → memberships → tasks/labels/subtasks → calendar/file links → activity. Seed updates only known fixture IDs. Backfill and repeat seed must not duplicate records or wipe arbitrary adopter rows; new metadata defaults must be tested on populated upgrades, not just a fresh fixture DB. Do not derive demo fixtures by querying DB or make DB results read fixture objects.
- New reads: `readProjects`, `readProject`, `readProjectTasks`, `readProjectTimeline`, `readProjectFiles`, `readProjectActivity`, `readWorkspaceHome`. Use required bounded `projectId` for scoped reads; optional validated task/status/assignee/label filters and deterministic bounded pagination. Project existence and child scoping are explicit. Empty project ≠ unknown project. Overview/Home aggregates use the same canonical tasks with stable progress/overdue rules, not hard-coded card numbers.
- Proposed metrics: active projects = active or at-risk; open tasks excludes done/canceled; completed = done; overdue = open, dated before the labeled sample reference date. Progress = done / non-canceled tasks, with 0% and “No tasks” when denominator is zero. My tasks uses a clearly named **sample member**, initially mapped Jordan Lee, in both demo and auth mode; it is not the real account's work. Selection is a read-only local filter, not membership editing. Upcoming excludes undated/terminal tasks, sorted due date then stable ID. Activity is explicitly sample history.
- Page payloads stay bounded: list page sizes 10/20/50; board/timeline batch at most 100 tasks with visible continuation, never silent truncation; Home uses limited sections with links to full project views and separately computed totals. Sidebar summaries exclude tasks/files. Implementations may choose lower limits if the UI explains them; any changed product scope needs review.

### Parity and failure matrix

**Home:** greeting with serialized request context; concise sample-data note; four KPIs; My tasks and upcoming deadlines; project progress table; recent sample activity. Desktop gives the task list the primary column and deadlines/activity a secondary column, then progress where scanning works. Mobile stacks greeting → KPIs → My tasks → deadlines → progress → activity, keeping complete labels and local table scrolling. Links go to the owning project/view; no fake creation buttons. Empty/filter-empty/loading/error states use the existing page-boundary vocabulary. Projects index uses search plus status filtering, compact rows/cards with name, description, status, progress, due date and members; default action opens Overview.

**Project shell / Overview:** stable project identity, breadcrumb back to Projects, status text, sample members, five wrapping or locally scrolling route links. One h1; view section headings are subordinate. Overview uses the same progress calculation and task/activity data as Home; files and upcoming work link to their respective views. Read-only metadata is text, not disabled form controls. Empty projects still show all usable view destinations and honest zero states.

**Board / List:** reuse tenboards Kanban cards/columns and Tasks table, with canonical statuses and the same IDs/counts. Board retains readable column labels/counts and local horizontal scrolling; mobile may stack columns or expose a status filter plus a clear List link, without dropping tasks. List adds assignee, due date, labels, subtask and comment counts with accessible headings and compact alignment. Search/filter/sort/pagination are real read-only interactions. A named task details disclosure/drawer may show full text/subtasks, with focus return and no mutation controls. No draggable cursors, completion toggles, Edit/Delete menus, Add task placeholders or save-success messages. Scope local UI state by project so filters/selection never leak stale content when navigating.

**Timeline (new):** CSS grid/positioned bars and existing date utilities are sufficient; no Gantt library, premium FullCalendar scheduler or new heavy charting package. Reuse existing Calendar in a read-only `mode=calendar` subview, not a separate top-level route. Validated `mode=gantt|table|calendar`, default gantt; calendar redirect selects calendar. Date range/scale controls (Weeks/Months, previous/next, current day) change presentation only; restrict visible range to 12 weeks or 12 months and explain clipping/continuation. Task row labels sit beside a horizontally scrolling date grid; bars have text/status cues and exact start/end available without hover. Single-day tasks use a one-day marker; undated items appear in an Unscheduled section, not silently dropped. Calendar events occupy a separately labeled section and are not double-counted as task completion.

The **accessible table fallback is always available**, with caption, task/event name, status, assignee, start, end, due date and duration/unscheduled text; it has the identical filtered dataset and order. It is the default presentation below the mobile breakpoint after hydration (initial SSR state remains consistent), with an explicit opt-in to the scrollable chart. No separate screen-reader-only stale dataset. The chart can be decorative when the table is shown; avoid duplicate announcements. Named horizontal scroll regions, standard keyboard controls, visible focus, no drag/resize/reorder and no hover-only content. Include a textual current-day label; color is supplementary. Preserve Calendar's SSR UTC-to-local transition, all-day exclusive-end semantics and live clock without freezing it. A bounded adapter converts task inclusive end dates to calendar exclusive all-day ends. No dependency connectors, critical path or resource planning in this milestone.

**Files:** reuse existing grid/list/folder cards scoped to project. Search/type filters and display switch work locally against loaded data; empty state names the project. Stars/sharing are labeled sample attributes. Show file metadata and optional details, not pretend upload, delete, share, new folder or download actions. No remote file fetching. Folder summary limitations from the data contract remain visible.

Guard **Home, Projects index, project layout and every child** through `requireAppRoute`; ensure aliases cannot bypass protection. Each new server function calls `requireSession`, then validates bounded input and queries only the requested project. Guard shell summaries and aggregate functions too; client hiding is not security. No raw SQL interpolation or arbitrary client-selected sort columns. Keep auth refresh, private/no-store, fail-closed configuration/storage errors, origin defenses and safe return URLs. Never expose credentials or auth membership in DTOs. Membership is not an ACL; do not implement a half-formed tenant boundary. Missing projects return not-found only after the auth boundary. No server function mutates project data in v0.8.
