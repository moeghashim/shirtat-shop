## Brief and boundaries

Template users must be able to run `npm install && npm run dev` with no env, database or Docker, then opt into the same content from local Postgres 17. Every data-bearing app page and all 14 dashboards, including all four legacy variants, move behind typed read functions. Production remains a demo Worker through v0.4; Neon hosting, Hyperdrive and production database setup belong to v0.6. Better Auth belongs to v0.5. No real CRUD, authentication, authorization, sessions, RBAC, uploads, message delivery or schema-driven UI framework.

Use `drizzle-orm` with `postgres` (postgres.js); `drizzle-kit` generates SQL committed under `src/server/db/migrations/`. These dependencies are pre-approved. Any other new runtime dependency requires escalation. Use existing Node 22+, npm, strict TypeScript, aliases, Biome and Playwright tooling. Keep `src/components/ui/`, `src/components/calendar/`, generated files, font/preferences registries and PLAN.md intact. No screen, shell or token redesign. Existing local edits, drag/reorder, forms and placeholder actions retain their exact semantics and never persist to the database.

The approved interface is `src/server/data/<domain>.ts`: typed reads with demo and db implementations behind one contract. Routes use TanStack Start server functions in loaders; components receive serializable loader data. No direct runtime fixture import from a route component, nested component or state store. UI-only mappings, pure calculations and type-only imports may remain client-safe after separation from fixtures. Do not send icon constructors or SQL/ORM objects across the boundary. Database client/config/queries remain server-only and lazy enough for Workers demo builds/runtime with no DB settings or connection attempt.

| Configuration | Required behavior |
| --- | --- |
| `DATABASE_URL` absent | Demo fixtures, zero config; Docker can be stopped |
| `DATABASE_URL` configured | Read actual Postgres data |
| `DATA_SOURCE=demo` | Force demo even if a configured database is broken |
| Configured DB unreachable, unauthorized or unmigrated | Visible safe load error through existing error UI; no silent fixture fallback |

Task 001 documents invalid/empty configuration handling and sanitizes failure output; credentials never reach browser bundles or error messages. Production gets no database binding/secret in this milestone. Demo-only preview uploads use `npm run preview:deploy`, never production deploy.

## Modelling, fixtures and parity contract

- Fixtures are the single seed source. Extract embedded data into plain fixture modules within the owning domain only where necessary; do not maintain a second handwritten seed dataset. Keep current IDs, values, relationships, optional/null semantics and display order. UI metadata (icons/classes/chart colors/control options) is not a database entity.
- Normalize natural entities and ordered child relations: users/roles, profile details, products, invoice parties/items, orders, events, files, messages, tasks, shipments, environments, patients and dashboard records. Separate fixture universes remain separate unless an existing relationship proves otherwise; names alone do not imply identity. No whole-fixture JSON blobs or generic JSON payload tables.
- Aggregate series without natural entities go in typed metric-points rows. Use explicit domain/series/point keys, typed values/units/dimensions and deterministic ordering. Preserve displayed KPI totals/deltas even when demo aggregates do not reconcile with a short illustrative list. Do not invent hidden records to force reconciliation.
- Migrations are cumulative and reviewed; only db commands migrate/seed, never app startup. Seed stable IDs transactionally and repeatably, respecting foreign keys and child order. Reseeding must not duplicate records or erase unrelated data. No automatic reset or destructive helper is planned. `docker compose up -d` is sufficient; any optional helper needs justification and explicit destructive safeguards.
- Dates and time are part of the interface. Fixed demo dates use explicit UTC or civil-date representations. Request-relative Calendar, Invoice and Mail fixtures use typed date/offset definitions plus one serialized request reference. Seed definitions, not a stale seed-time rendering. Both implementations receive the same reference/inputs; tests cover later requests after seed, rollover and timezones. Retain Calendar's post-hydration local month/wall time and real Today, and all prior hydration fixes. No frozen application clocks, `suppressHydrationWarning` or SSR disabling.
- Each task registers **every** exported domain read and supported input/variant scenario in the parity inventory. Proposed domain names below establish ownership; exact function names settle in task 001/domain PRs and must appear in the registry and docs. Parity invokes actual demo and DB implementations with identical context against seeded Docker Postgres, compares exact typed results including ordering/precision/nulls, and fails nonzero on mismatch, missing coverage or DB failure. It must not simply compare seed objects with themselves.
- Source-independent projections may format/derive loaded records for UI behavior. Range-driven chart generators (notably Analytics V1) require explicit data-layer ownership and parameter parity; they are not exempt client signals. Only genuinely simulated monitoring waveforms/trends/live ticks stay computed client-side, with baseline patient data loaded normally.
